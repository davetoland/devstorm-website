What we do

Agentic engineering, not vibe coding.

Devstorm builds software for you using agentic engineering. This means we can help you build what you want, faster, at a lower cost.

We've built a toolkit that cuts the time needed for research, investigation, planning, implementation, testing, deployment, and documentation. Work that would usually need a larger team gets done faster, while the important decisions and control stay with you.

Experienced human engineers own the parts that matter: architecture, technical decisions, and what finally ships. AI does the painful, time-consuming, error-prone work in between.

Getting started

Understand the project before changing it.

Most codebases were not built with agents in mind. Before any agent changes your code, we build the grounding knowledge that agents need to work in yours. It starts with an agreed scope, works from evidence, and asks you only about what the evidence cannot settle.

  1. 01

    Agree access and scope

    You confirm the repositories, projects, permissions, and approval points. Having access to something does not put it in scope.

  2. 02

    Inspect before asking

    We read the authorised repositories, work tracker, documentation, and decision records. Facts the project can supply are ours to find, not yours.

  3. 03

    Propose, then confirm

    We show you what we found, as interpretations to confirm or correct. Questions come only when the answer changes something.

  4. 04

    Write it down

    We record the working agreement in a project profile that your team can read, review, and edit, with or without the toolkit.

The delivery process

From a rough idea to a reviewed change.

Not every change needs every stage. A small, well-understood fix can go straight to implementation and validation. An uncertain problem needs investigation first.

  1. 01

    Discovery

    Whether we're starting from a brief, a problem statement, a need, or a goal, we separate the knowns from the unknowns, brainstorm ideas, prototype solutions, and clarify assumptions.

  2. 02

    Refinement

    From there we decompose and refine, identify requirements, define acceptance criteria, and understand the scope. We keep iterating until we have clarity.

  3. 03

    Planning

    Then we create technical plans, define the objectives, specify bounded changes, crystallise the decisions, and make them implementation-ready.

  4. 04

    Implementation

    Generate code, configuration, schemas, tests, and documentation according to the agreed plans, architecture, engineering standards, and acceptance criteria.

  5. 05

    Validation

    Run tests, static analysis, security scans, and performance checks. Verify behaviour, detect regressions, and feed findings back with the evidence to support them.

  6. 06

    Review

    Review changes for clarity, maintainability, and alignment. Assess validation evidence, challenge assumptions, and resolve outstanding findings.

Our toolkit

The engineering process, distilled.

We designed the skills, workflows, and harness extensions ourselves, then evaluated and refined them through real delivery. Each skill has a defined job, a clear scope, and a point where it stops.

How and why the code and environments work, and what effect change will have.

Codebase understanding
An evidence-based account of how a subsystem or runtime flow actually works.
Rationale understanding
The reasons behind the existing design, recovered from history and project records.
Change impact
The effects of a proposed change, with its risky assumptions tested.
Research

SHAPING

Discovery

Brainstorming
Develop, challenge, and compare ideas before choosing a direction.
Prototyping

Refinement

Implementation

Software design

The toolkit also has skills for writing for a human audience. Pull requests, work items, and documentation follow a technical writing standard based on Simplified Technical English, with a final pass that removes vague and inflated wording.

Workflows & strategies

ORCHESTRATION

Agents that coordinate other agents and subagents, with clear briefs, ownership, and budgets. Their work is monitored, and the results are combined and verified.

CONTEXT MANAGEMENT

A strategy to manage context on longer-running tasks: predicting operations that will load heavy or transient data, knowing when to checkpoint, and when to start fresh.

PAIR PROGRAMMING

Two agents with separate contexts, working as a driver and navigator pair. They tackle a single problem by exchanging information, rather than in an adversarial capacity.

RESEARCH-PLAN-CODE

A staged workflow for work with high uncertainty, consequence, or context burden. Each stage produces compact evidence for human review, with a checkpoint before the next.

FACTORY MODE

Delivers a scoped engineering outcome end to end, adapting skill use, delegation, human checkpoints, context, and verification to the uncertainty, consequence, and time involved.

Harness extensions

SESSION EVALUATION

Traces what each agent and subagent did in a session, and why. Actions, decisions, tool usage, effectiveness, and behaviour can then be evaluated and reasoned about, for continuous improvement.

TMUX MULTI AGENTS

Wraps the terminal in a tmux session. Agents can launch in separate windows and panes, and interact with each other. Split, join, rename, or kill them at will, for full control of running agents.

SCOPED INSTRUCTIONS

Conditional instructions, matched by pattern, that load only when a specific file, file type, project, or folder comes into scope. Fine-grained rules reach the agent's context only where they apply.

SKILL READ DEDUPE

Stops agents wasting context by loading skills that are already present and unchanged. Handles the cases where compaction, a session clear-down, or a skill change genuinely needs a reload.

TUI ENHANCEMENTS

A status bar in the terminal footer that keeps token spend, context usage in tokens and as a share of capacity, the current branch, and the current worktree in view at all times.

Not all agent harnesses can be customised in every way. We'll work with you to apply the extensions that matter to your business, based on your choice of harness.

Containerisation

Freedom inside a fence.

An agent that has to keep asking your permission before it reads a file, makes a change, installs a package, or runs a command is slow, and makes you the bottleneck.

An agent running unrestricted on your own machine can reach every repository, document, credential, and tool that you can. That can lead to unexpected outcomes. Nobody wants to find that an agent has deleted the production database, or published a secrets file to the internet.

Telling an unrestricted agent not to read or use something is a soft boundary. If you also give it a task that needs those things, the instructions conflict, and it may decide that completing the task matters more.

That is not the agent being bad, or 'going rogue'. It is trying to complete the task you gave it, with the capabilities you made available.

The solution is not to lock the agent down and make it ask permission for everything it might need to do. Nor is it to hand over the keys to the kingdom and politely ask it not to use them, even if it later judges that it needs to.

The solution is a strictly contained environment: a ring-fenced boundary where you control the permissions, access rights, and credentials, and the agent has complete freedom to work inside it.

  1. 01 · Build the fence

    A dedicated container provides a Git-controlled project workspace. Network settings and mounted volumes limit what else it can reach.

  2. 02 · Pass in the keys

    Scoped credentials, access tokens, permissions, and settings are injected as environment variables at launch.

  3. 03 · Let it loose

    The agent runs in unrestricted mode. It can install packages, add CLI tools, read and change files, and reconfigure its system as the work needs.

  4. 04 · Review what comes out

    Git commits and pull requests show what the agent changed. Tests show whether it works. People review the changes and decide what to keep.

Only the keys it needs

Fine-grained tokens grant only the permissions the agent needs. An agent might view the main branch but not commit to it, or inspect the release pipeline but not trigger a deployment. An agent cannot use access it was never given.

Disposable by design

If an agent breaks its environment, we discard the container and start a new one. If a change breaks the codebase, we roll it back or discard it and start again. Your machine, other projects, and credentials are unaffected.

Tripwires inside the fence

Hooks check actions before they run, and block those that match a rule, such as commits to protected branches, destructive commands, or edits to secrets. Repository policies on the remote add further layers of protection.

Isolated parallel work

Each agent checks out and branches code in its own workspace, and parallel subagents each get their own worktree. Every change is isolated to the agent that made it, the same way a human development team works.

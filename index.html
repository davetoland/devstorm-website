Speed is the easy part.

An engineer who misunderstands a task loses half an hour before someone notices. An agent that misunderstands the same task can change dozens of files, write tests that agree with it, update the documentation, and spend a real budget doing all of that.

The answer is not to approve every step, which only turns people into the bottleneck. Human judgement sits at the points where a mistake would compound. Around those points, agents take on the work that used to eat the time: finding and cross-checking scattered guidance, closing research gaps, working through technical spikes, turning rough ideas into prototypes people can react to, and producing the structured output that follows every decision.

  • Intent before autonomy

    We confirm the direction before agents start running. A short conversation up front is cheaper than a confident agent heading the wrong way.

  • Use what is already known

    If the answer is already in the code, the tests, or the project's records, agents use it. You are not asked questions that have already been answered.

  • Escalate judgement, not work

    You decide intent, trade-offs, and risk boundaries. You also decide where agents must stop for guidance before an irreversible step. Agents do the investigation around those decisions.

  • Validate outcomes, not activity

    A green build proves that something ran. It does not prove the change does what was asked. Tests are based on acceptance criteria that people set, and every result is verified against them.

  • Keep the codebase coherent

    Code can be correct in isolation and still be a poor fit for the codebase around it. Agent-written code follows the patterns already in place, and stays readable to your engineers.

  • The assigned work, and only that

    Agents make the change the acceptance criteria need. They do not refactor, rename, or tidy code beyond the task. When they see a possible improvement, they report it separately for you to decide on.

From a rough idea to a reviewed change.

Not every change needs every stage. A one-line fix does not need a discovery phase. The amount of process matches the size and uncertainty of the work.

  1. 01

    Discovery

    Start from an idea, a problem, or a 60-page specification. Separate what is known from what is assumed and what is still open.

  2. 02

    Refinement

    Take the work to the next useful level of detail, until it can be built without anyone inventing what you meant.

  3. 03

    Planning

    Write a technical plan based on how the system actually works today, not on how the documentation says it works.

  4. 04

    Implementation

    Change code, configuration, schemas, infrastructure, tests, and documentation, inside the agreed scope.

  5. 05

    Validation

    Produce evidence that the change meets the intent and the acceptance criteria. A skipped check is not a pass.

  6. 06

    Review

    A separate reviewer decides whether the change is good to merge, and forms that view before reading the author's argument for it.

The toolkit

More than 40 skills, each with one job and a clear place to stop.

Every skill is hand-built and refined through iteration, evaluation, and real delivery. Each one has a defined responsibility, firm boundaries, and an explicit stopping point. A request to investigate a bug does not quietly turn into a fix in production code.

Give it an outcome, not a script.

Describe the job, the source material, and your limits. The lead agent checks the requirements and your project rules, states its strategy, and gets on with it.

It might keep tightly linked work to itself, hand independent pieces to subagents, or move through research, planning, and implementation in phases. It changes approach when the evidence says so, and it stops at the boundary you set. It asks you about intent and authority, not about routine choices.

Extensions to the coding agent harness encode engineering conventions and guardrails. Your project rules still decide what happens to branches, pull requests, merges, and deployments.

Agent and subagent management

The lead agent keeps its own context lean, because every turn resends it. Long, noisy, or independent work goes to subagents. Small, tightly linked work stays put.

Session tracing

Contained environments

Getting started

Before agents touch your code, they learn it.

Most codebases were not built with agents in mind. The first thing the toolkit does is build the grounding knowledge agents need to work in yours. It works from evidence, and asks you only about what the evidence cannot settle.

  1. 01

    Inspect before asking

    It reads the repository, source control, work tracker, documentation, and any existing decision records. Facts the project can supply are its job, not yours.

  2. 02

    Agree the scope

    You confirm which repositories, projects, and teams it may work in. Having access to something does not put it in scope.

  3. 03

    Propose, then confirm

    It shows you what it found as interpretations to confirm or correct. There is no setup questionnaire. Questions come only when the answer changes something.

  4. 04

    Write it down

    It records what it learned in a project profile that your team can read and edit, with or without the toolkit.

What it establishes

  • How your work items, fields, and links map to the way agents refine and plan work.
  • What agents may and may not do in source control, including branches, commits, pull requests, and merges.
  • Where architecture decisions live, and how agents find only the ones that apply to a task.
  • One home for your domain model and its terms.
  • Project-specific skills, where your local procedures need them.

It never writes credentials into the repository, and it never rewrites your existing agent instruction files. Run it again when things change. It reconciles the differences and keeps your edits.

Contained autonomy

Freedom inside a fence.

An agent that has to ask before it reads a file or runs a test is not much use. You become the bottleneck again. An agent with the run of a developer's machine can reach every repository, token, and cloud session on it.

Telling an agent what not to touch is a soft boundary. Given a task and a way around a restriction, agents sometimes take it. So our agents work in containers. Each one gets a full development environment, but it sees only what we put inside: the project workspace, the tools the work needs, and credentials scoped to what it is allowed to do. It cannot reach production, because production is not in its world.

Scoped credentials

Credentials are injected deliberately, and fine-grained tokens grant only what the work needs. An agent might be able to view the main branch but not commit to it, inspect the release pipeline but not trigger a deployment, or know that a key vault exists without being able to read its contents.

Tripwires inside the fence

Hooks stop dangerous actions before they run, such as commits to protected branches, destructive commands, or edits to secrets. The container limits what an agent can reach. Hooks limit what it can do there.

Isolated parallel work

Each agent that writes in parallel gets its own worktree or clone and its own branch, so every file has one writer and agents cannot overwrite each other's changes. Agents that only need to read get read-only access.

What agents learn should outlast the session.

Every agent session starts cold. Without a record, you are onboarding a brilliant new senior engineer every morning, and each one rediscovers the same facts or guesses why the system is shaped the way it is. The toolkit records what is established as fact, which decisions were made, and why. Anything surprising, or likely to come up again, is written down with its reasoning, where both people and agents can find it.

  • Decisions and their reasons

    Code shows what was built, not why. Consequential decisions are recorded with the alternatives considered and the reasons they were rejected.

  • One domain language

    The domain model and its terms live in one place, so people and agents use the same words for the same things.

  • Kept only if it matters

    A finding becomes permanent only when future work benefits from it. Task notes and handoffs are short-lived, so they do not pile up as clutter.

  • In your repository, under review

    Knowledge lives in your repository, unless you already have an established home for it. Project-specific agent instructions go through your normal review and approval, like any other code.

Adapts to how you already work.

The toolkit does not impose a tracker, a work-item hierarchy, a branching model, a language, or an agent harness. It reads your conventions from the repository first, and asks you only about what it cannot find.
